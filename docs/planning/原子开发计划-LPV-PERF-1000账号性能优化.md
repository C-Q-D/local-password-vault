## 总体计划

- 产品交付单元：在不改变现有功能、安全边界和文件格式的前提下，优化个人密码库最多 1000 个账号时的资源使用和常用界面计算。
- 目标结果：连续复制密码不按次数创建休眠系统线程；1000 个账号的列表渲染不重复执行相同过滤、排序、分类查找和时间格式器构造；Rust 快照使用单次账号遍历统计分类数量。
- 验收场景：快速连续安排多次密码清理时只执行最新任务且后台线程数量恒定；1000 个账号列表得到与现有排序、分类和时间显示相同的结果；50 个分类、1000 个账号的快照数量准确且生成时间不劣于基线。
- 明确排除：超过 1000 个账号、数据库、分页、虚拟列表、搜索索引、文件格式变化、弱化 AES-256-GCM/DPAPI/原子替换、Release 构建和无数据支持的搜索改造。
- 已确认架构：`src-tauri/src/commands/vault.rs` 当前每次复制密码调用 `thread::spawn` 并休眠 30 秒；`frontend/src/app/App.svelte` 在一个渲染中多次调用 `visibleAccounts`，逐行线性查分类并逐行构造 `Intl.DateTimeFormat`；`crates/vault-app/src/lib.rs::snapshot_from` 为每个分类重新扫描全部账号。
- 数据与安全不变量：模拟账号只在隔离测试进程内存或自动清理的临时目录中生成，不进入正式密码库；密码清理仍只在剪贴板内容和写入凭证匹配时执行；性能优化不得把密码或备注加入前端快照，不得减少保存认证步骤。
- 基线数据：Node 24 下模拟 50 分类、1000 账号的当前前端一次等效渲染中位数 42.033ms、P95 42.678ms；Debug `vault-app` 200 次测量的平均快照 1738µs、平均搜索 941µs。临时模拟账号测试文件已删除，仓库和正式密码库未留下测试数据。
- 执行模式：连续执行；每个原子完成验证、独立提交、推送和汇报后自动进入下一原子。
- Git 策略：按仓库规则在当前 `master` 分支逐原子提交，并同步到上游 `origin/master`。
- 原子顺序：`LPV-PERF-01` → `LPV-PERF-02` → `LPV-PERF-03`。
- 整体回归：受影响 Rust Crate 聚焦测试和 check、`npm run check`、`cargo test --workspace`、运行中 Tauri Debug 增量编译和 HMR；不执行 Release。

## LPV-PERF-01 使用单一线程调度密码清理

- 状态：done
- 支持的验收场景：连续复制密码时资源占用不随尚未到期的复制次数增加，最后一次复制仍在 30 秒后按凭证条件清理。
- 唯一目标：把每次复制密码创建休眠线程改为全程序单一后台调度线程。
- 当前行为与目标行为：当前每次成功复制密码都 `thread::spawn` 一个休眠 30 秒的线程；完成后应用启动时只创建一个清理调度器，新任务替换旧任务并重置 30 秒截止时间。
- 前置条件与依赖：现有 `PasswordClipboardReceipt::clear_if_owned` 已原子比较剪贴板序列和 token 后清理。
- 代码定位依据：新增 `src-tauri/src/password_clear_scheduler.rs`；在 `src-tauri/src/lib.rs` 组装并托管；`src-tauri/src/commands/vault.rs::copy_account_password` 只提交清理凭证。
- 允许修改：上述 Tauri Rust 文件、调度器单元测试和本原子状态。
- 明确不修改：剪贴板 token/序列算法、30 秒产品规则、账号使用次数、前端接口、密码库文件和其他 command。
- 实现步骤：使用一个 `mpsc` 接收端和具名后台线程；调度器持有唯一发送端；工作线程无任务时阻塞，有任务时用 `recv_timeout` 等待截止；新凭证到达时替换旧凭证并重新计时；发送端断开时立即尝试清理最后凭证并退出；调度提交异常时 command 立即按原凭证尝试清理并返回现有剪贴板失败语义。
- 接口、数据与错误契约：Tauri command 名称和成功响应不变；只在 Rust 内部移动清理凭证；不得把密码、token 或凭证返回前端。
- 边界与异常：旧凭证被新凭证替换是安全的，因为新复制已改变剪贴板序列；清理失败沿用当前忽略策略，不阻塞主程序；工作线程不得忙轮询。
- 测试要求：短延迟测试证明 100 个快速任务只有最后一个执行；新任务重置截止时间；发送端断开会清理待处理任务并退出。
- 验证命令：`cargo test -p local-password-vault password_clear_scheduler`；`cargo check -p local-password-vault`；运行中 Tauri Debug 增量编译；`git diff --check`。
- 预期结果：应用生命周期内密码自动清理最多占用一个后台线程，既有复制和条件清理行为不变。
- 完成判定：调度器聚焦测试及 Tauri check 通过，DDD 并发与清理语义审查通过，Debug 增量编译成功。
- 交付给下一原子的输出：密码复制不再是操作次数相关的线程资源增长点。
- 停止或重新规划条件：`PasswordClipboardReceipt` 不能安全在线程间移动，或替换旧凭证会破坏现有条件清理不变量。
- 风险等级：L3。
- DDD 门禁：实现前隔离质疑“保留最新凭证并由单一线程调度不会误删用户内容或遗漏当前密码清理”。
- 计划提交信息：`perf(clipboard): [LPV-PERF-01] 合并密码清理线程`。

## LPV-PERF-02 复用账号列表派生结果

- 状态：done
- 支持的验收场景：1000 个账号下列表数量、表格和空状态共享同一排序结果，分类名称及最近使用时间保持正确。
- 唯一目标：同一前端状态版本只计算一次可见账号列表，并复用分类映射和时间格式器。
- 当前行为与目标行为：模板当前最多四次调用过滤排序函数，每行线性查找分类并新建时间格式器；完成后使用一个显式依赖的响应式列表、一个分类 Map 和一个共享格式器。
- 前置条件与依赖：现有账号排序、分类过滤和空状态行为已经由用户确认。
- 代码定位依据：`frontend/src/app/App.svelte` 的 `visibleAccounts`、`formatLastUsed`、`accountCategoryName` 及账号表格模板。
- 允许修改：该 Svelte 文件、本原子状态和只读临时基准脚本；模拟数据不得提交。
- 明确不修改：搜索 command、排序规则、分类含义、表格字段、后端 DTO、CSS 和界面布局。
- 实现步骤：把 `vault`、搜索文本、分类、搜索结果和排序方向作为显式参数生成响应式 `currentVisibleAccounts`；由当前分类摘要生成 `Map`；模块加载时构造一个 `Intl.DateTimeFormat`；模板所有数量、表格和空状态引用同一派生结果。
- 接口、数据与错误契约：不新增 IPC；未分类和未知分类文案保持不变；未使用账号仍排在有记录账号之后；相同时间继续保持原顺序。
- 边界与异常：必须显式声明响应式依赖，不能把 `vault`、分类或搜索文本隐藏在仅由函数体读取的旧式响应式语句中。
- 测试要求：`svelte-check` 无错误警告；静态检查确认模板不再直接多次调用 `visibleAccounts` 且格式器只构造一次；用 50 分类、1000 模拟账号重复同一 Node 基准并记录中位数/P95。
- 验证命令：`npm run check`；1000 账号聚焦基准；运行中 Vite HMR；`git diff --check`。
- 预期结果：可见账号排序每个状态版本只执行一次，结果与当前行为一致，前端等效渲染耗时显著低于 42ms 基线。
- 完成判定：检查与 HMR 通过，1000 账号基准无行为差异且耗时下降。
- 交付给下一原子的输出：前端已消除当前明确的重复计算热点。
- 停止或重新规划条件：Svelte 响应式依赖无法稳定覆盖账号数据、分类、搜索和排序变化。
- 风险等级：L1。
- DDD 门禁：不适用；结果可由类型检查、静态检查和合成基准直接证明。
- 计划提交信息：`perf(frontend): [LPV-PERF-02] 复用账号列表派生结果`。

## LPV-PERF-03 单次遍历统计分类账号数

- 状态：done
- 支持的验收场景：50 个分类、1000 个账号的分类数量、未分类数量和账号摘要完全准确。
- 唯一目标：`snapshot_from` 用一次账号遍历生成分类计数。
- 当前行为与目标行为：当前每个分类都重新过滤全部账号；完成后先用 `HashMap<Uuid, usize>` 和独立未分类计数进行一次聚合，再生成分类摘要。
- 前置条件与依赖：现有领域校验保证账号引用的分类存在；前端 DTO 不变。
- 代码定位依据：`crates/vault-app/src/lib.rs::snapshot_from` 及同文件现有快照测试模块。
- 允许修改：`vault-app` 快照实现、聚焦测试、本原子与总体计划状态、活动计划索引。
- 明确不修改：`VaultSnapshot` 字段、账号顺序、使用事件、搜索、加密存储和前端。
- 实现步骤：预分配分类计数 Map；单次遍历账号累加分类或未分类数量；分类摘要按原分类顺序读取计数；账号与事件摘要仍按原顺序映射。
- 接口、数据与错误契约：快照结构和序列化调用方保持兼容；不存在账号的分类返回 0；未分类计数准确。
- 边界与异常：不得通过跳过领域校验容忍悬空分类；性能实现不改变已确认文档所有权和克隆安全边界。
- 测试要求：增加 50 分类、1000 账号聚焦测试验证总数、每类数量、0 账号分类和未分类数量；复用隔离基准记录优化后的 200 次平均快照耗时；运行 `vault-app` 测试。
- 验证命令：`cargo test -p vault-app snapshot`；1000 账号聚焦基准；`cargo check -p vault-app`；`cargo test --workspace`；`git diff --check`。
- 预期结果：快照计数复杂度由分类数乘账号数降为分类数加账号数，1000 账号下耗时不劣于 1738µs 基线。
- 完成判定：聚焦测试、基准、Crate check 和 Workspace 回归通过，模拟数据和临时测试文件已删除。
- 交付给下一原子的输出：性能优化计划完成，无后续原子。
- 停止或重新规划条件：单次统计需要改变公开快照结构或账号顺序。
- 风险等级：L1。
- DDD 门禁：不适用；计数结果和兼容性可由直接测试证明。
- 计划提交信息：`perf(app): [LPV-PERF-03] 单次统计分类账号数`。
