# Rust / Tauri 编译策略

## 1. 目标

本项目使用 Rust、Tauri 2、Svelte、TypeScript 和 Vite。本策略的目标是缩短日常修改后的反馈时间，避免把 Release 全量编译错误地用于每一次代码改动。

核心原则：

1. 先选择能证明本次改动的最小检查。
2. 前端改动优先使用 Vite HMR，不重新编译 Rust。
3. Rust 改动优先 `cargo check` 和目标 Crate 测试。
4. 功能切片完成后才运行 Workspace 全量测试。
5. 只有交付候选或用户明确要求发布包时才执行 Release 构建。
6. 不日常执行 `cargo clean`，不无故删除 `target`。

## 2. 构建层级

### L0：无需编译

适用范围：

- 只修改 Markdown、产品文档或不参与打包的静态说明；
- 只进行只读分析。

验证方式：

- 检查 Git diff；
- 检查文档链接和事实一致性。

不得运行 Cargo、Tauri 或前端构建。

### L1：前端热更新

适用范围：

- Svelte 组件；
- TypeScript 前端状态；
- CSS、图标和静态资源；
- 不改变 Rust command 契约的界面调整。

验证顺序：

```text
前端静态检查或类型检查
  -> 受影响的前端测试
  -> 已运行 tauri dev 时由 Vite HMR 刷新界面
```

只修改前端时不得因为习惯重新执行 Rust Release 构建。需要真实桌面能力时可以保持一个 `tauri dev` 进程持续运行，不为每个文件重新启动。

### L2：Rust 快速检查

适用范围：

- 单个 Rust Crate 内的业务逻辑；
- 不改变发布配置和依赖集合的普通 Rust 修改。

验证顺序：

```bash
cargo check -p <受影响的-crate>
cargo test -p <受影响的-crate> <可选测试过滤词>
```

只有需要观察真实窗口、平台 API 或前后端调用时，才继续运行 Tauri 开发程序。

### L3：集成检查

适用范围：

- 修改 Tauri command 契约；
- 修改多个 Crate；
- 修改加密、持久化、文件锁、剪贴板或平台适配；
- 完成一个可独立验收的功能切片。

验证顺序：

```text
受影响 Crate 的 cargo check
  -> 受影响 Crate 的测试
  -> 前端类型检查和受影响测试
  -> cargo test --workspace
  -> tauri dev 真实路径冒烟
```

除非改动只在 Release 模式出现，否则本层仍不默认执行正式打包。

### L4：发布构建

只在以下情况执行：

- 用户明确要求重新编译可交付软件；
- 当前功能范围全部完成，准备人工验收；
- 修改了发布配置、安装包、签名或 Release profile；
- 需要测量最终启动、内存、包体积或 Release 专属行为。

验证顺序：

```text
前端生产构建
  -> cargo test --workspace
  -> Tauri Release 构建
  -> 启动最终产物
  -> 按验收清单检查真实功能
```

Release 构建失败时先修复失败原因，不使用清空所有缓存作为第一反应。

## 3. Cargo Profile

项目根 Workspace 的 `Cargo.toml` 应保持以下开发方向：

```toml
[profile.dev]
incremental = true
opt-level = 0
debug = 1
codegen-units = 256
lto = false

[profile.test]
incremental = true
opt-level = 0
debug = 1
```

- `dev` 和 `test` 使用增量编译。
- 开发阶段不启用 LTO。
- Release profile 只为最终产物优化，不用于日常反馈。
- 不把所有依赖随意打开 `all-features`，只启用当前实际需要的 Cargo features。

## 4. 缓存规则

- 保留 Cargo 的 `target` 目录；它必须在 `.gitignore` 中，但不应在每次任务结束后删除。
- 不执行日常 `cargo clean`。
- 不因普通编译错误删除 Cargo registry、Git cache 或前端包缓存。
- 固定 Rust stable 工具链和锁文件，避免无意义升级导致依赖重编译。
- `sccache` 主要用于第三方依赖、CI、新工作区和缓存恢复；本地频繁修改 Workspace Crate 主要依靠 Cargo incremental。
- 使用多个 Git worktree 时可以共享 Cargo registry 和 Git cache；共享 `target` 前必须避免多个 Agent 同时执行大型构建造成锁等待。

## 5. 会触发大量重编译的操作

执行前必须确认确有必要：

- `cargo clean` 或删除 `target`；
- 切换 Rust toolchain；
- 切换 target triple；
- Debug、Test、Release profile 来回切换；
- 修改 `Cargo.toml` features 或大范围更新 `Cargo.lock`；
- 修改 `build.rs` 或影响其输入的环境变量；
- 给所有依赖开启新 feature；
- 每个 worktree 使用完全独立且一次性的 Cargo 缓存；
- 每次前端调整都重启 `tauri dev`；
- 每个小修改都执行 `tauri build`。

## 6. 按文件类型选择验证

| 改动类型 | 默认验证 | 不默认执行 |
|---|---|---|
| 文档 | diff 和链接检查 | Cargo、前端构建 |
| Svelte / CSS | 前端检查、HMR、相关测试 | Rust Release 构建 |
| TypeScript 调用 | 前端检查、相关测试；契约变化时检查 command | 全量发布打包 |
| 单个 Rust 核心模块 | 目标 Crate `check` + 相关测试 | 整个 Tauri Release |
| Tauri command | Rust/前端相关检查 + `tauri dev` 冒烟 | 无理由清缓存 |
| 加密或存储 | 相关测试 + Workspace 测试 + 隔离数据集成测试 | 直接操作正式密码库 |
| 平台适配 | 目标平台测试 + 真实开发包冒烟 | 用 Windows 结果代替 Mac 验证 |
| 发布配置 | 全量测试 + Release 构建 + 最终产物冒烟 | 只看编译成功 |

## 7. 多 Agent 与 Worktree

- 可以并发编写互不覆盖的文件。
- 同一 Rust Crate 的核心文件默认由一个 Agent 负责，避免频繁失效和合并冲突。
- 前端和独立 Rust Crate 可以并行开发。
- 大型编译和最终 Release 构建由主 Agent 串行执行。
- 子 Agent 完成后报告修改文件和已运行的最小检查，主 Agent不机械重复相同检查。
- 合并后只运行能够覆盖跨模块交互的补充检查和最终验收。

## 8. 禁止把缓存误判为交付物

以下内容不提交到 Git：

- `target/`；
- `node_modules/`；
- 前端开发服务器缓存；
- Tauri 临时构建目录；
- `sccache` 数据；
- 测试临时密码库；
- 安装包之外的中间产物。

最终交付只保留可复现源码、锁文件、必要配置、测试和明确要求的发布产物。
